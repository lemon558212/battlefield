# GDD/17 — UE5 遷移評估

> 2026-08-02 建立。評估「《戰場》從 Godot 4.7 遷到 Unreal Engine 5」的成本、收益與風險。
> 本文只做評估與建議，**不是已核定的方向**。結論需使用者拍板。

---

## 一、先把現況量出來（不靠印象）

| 項目 | 實測數字 | 遷移意義 |
|------|---------|---------|
| GDScript 總量 | **18,610 行**（`Main.gd` 8,210 行、`Unit.gd` 2,698 行、`Terrain.gd` 1,060 行） | 全部要重寫，Main.gd 是單體，無法漸進搬 |
| 資料層 | 15 個 JSON（`class_base` / `maps` / `weapons` / `story`…） | **引擎無關，可 100% 帶走** |
| 自動化探針 | **20+ 支**（walk/stress/play ＋ ObbProbe/MobilityProbe/PadProbe…） | 全部 Godot 專屬，要重建 |
| `await` 協程 | **474 處** | ★最大障礙，見 §三 |
| `get_tree()` | 309 處 | 場景樹存取模式不同，逐處改寫 |
| `Transform3D` | 107 處 | 座標系與手性不同（見 §三） |
| `SurfaceTool` 程序化幾何 | 56 處 | 地形／建築／樹／石頭／載具全是程式生成 |
| `Skeleton3D` / 重定向 | 54 處 ＋ 自寫 `Retarget.gd` 459 行 | ★UE5 的明確收益，見 §四 |
| `MultiMesh` 實例化 | 24 處 | 對應 UE5 的 ISM/HISM，概念相通 |
| 美術資產 | 303 fbx／271 png／241 gltf／45 glb／102 blend | 大多可直接進 UE5，**這部分不會白費** |
| GDD 文件 | 17 份 | 引擎無關，全部保留 |

開發硬體：主力機 **RTX 5060 Laptop（8GB VRAM）**，另有一台 **64GB VRAM** 的機器（共用帳號，Claude 無法跨機器執行）。

## 二、UE5 確實能解的痛點

1. **渲染品質／「材質太暗」**
   目前反覆出現的問題（石頭變黑剪影、岩石讀成紫褐、立繪模型太暗）本質是
   「自己調 PBR 參數 × 頂點色 × 色調相乘」很難收斂。UE5 的 Lumen ＋ 成熟 PBR
   工作流在這件事上是壓倒性的，這是最實在的收益。

2. **動畫重定向**
   現在是自寫的 `Retarget.gd`（459 行）＋ UAL mocap 庫即時重定向，
   「重定向 20 對骨」是每次生成都要做的事。UE5 的 IK Rig / IK Retargeter 是
   產品級工具，且立繪生成模型的骨架差異問題在那裡有標準解法。

3. **載具「太陽春」**
   嚴格說這不是引擎限制（現在是程序化生成的低多邊形車體），但 UE5 的
   Fab／Quixel 免費資產庫有大量可直接用的高品質載具，等於繞過自己建模。

4. **載具與角色物理**
   Chaos Vehicle、膠囊碰撞、地形貼合都是現成的，不必像現在自己寫
   `_settle` / `_support_height` / `_resolve_solids`。

## 三、UE5 解不了、或會讓事情變糟的部分

1. **★立繪本人模型臉部糊掉——換引擎完全無助**
   這是生成模型（Hunyuan mini 0.6B）的能力上限，屬於**資產生成**問題，
   不是渲染問題。真正的解法是在 64GB 那台跑 TRELLIS.2 4B（已備好 `tools/gen3d`），
   跟用什麼引擎無關。這點很重要：如果換 UE5 的動機包含「讓角色像立繪」，
   那動機無法被滿足。

2. **★474 處 `await` 是最大的單一障礙**
   整套驗收方法論建立在 GDScript 協程上——`await _hold_key(KEY_W, 6.0)`、
   `await _snap(...)`、走查逐點取樣。UE5 沒有等價物：C++ 要用 Latent Action /
   TimerManager 重寫，Blueprint 的 Delay 不能用在需要精確控制的測試裡。
   **「用走的／用打的量出數字」這條驗收鐵律，是靠這 474 處 await 實現的。**

3. **★已修好的物理正確性會歸零重踩**
   `_settle` 的交替迭代（邊界卡人）、OBB 車體碰撞（穿過車尾）、地基墊系統、
   `terrain_mobility` 的 `null` 語意（軍艦上陸）、逃生位移不可送進另一種
   不合法狀態（ch07 那 3357 筆）——這些都是**在遊戲裡實測出來的邊界情況**，
   不是抄得到的知識。UE5 的 Chaos 能接手一部分底層碰撞，但
   「蹲在 1.3m 沙包後軀幹被擋、站起來頭露出」這類戰術判定仍要自己寫，
   而且每一個坑要重踩一遍。目前 **30/30 章 0 FAIL** 是好幾週的累積。

4. **★8GB VRAM 是實務上最大的風險**
   UE5 編輯器開 Lumen/Nanite 在 8GB VRAM 上會非常吃緊（實務門檻普遍在 12GB+）。
   主力開發機體驗劣化，直接衝擊最關鍵的資源：**迭代速度**。
   而 64GB 那台是共用帳號、Claude 無法跨機器執行，不能當日常開發機。

5. **編譯循環 vs 現在的「改完立刻跑」**
   現在的節奏是「改 .gd → 立刻 headless 跑 30 章 → 看 FAIL」。
   UE5 的 C++ 專案首次編譯 20~40 分鐘，之後增量也是分鐘級；
   headless 自動化（Gauntlet / Functional Testing）能做，但要先建整套框架。
   目前的修→重測循環到 0 FAIL 的工作方式，會顯著變慢。

6. **「免建置」鐵律徹底放棄**
   專案鐵律 2 已為 Godot 讓過一次（vendored three.js → 換真 3D）。
   UE5 是另一個量級：沒有「開瀏覽器即玩」，手機版要另做，
   GitHub Pages 的「push 即更新、手機可玩」那條線會消失。

## 四、成本粗估

| 階段 | 內容 | 粗估 |
|------|------|------|
| 垂直切片 | 一章可玩：地形＋一個兵種＋移動＋射擊＋一台載具 | 中 |
| 核心規則移植 | CP/AP、警戒射擊、命中傷害、迷霧視野（規則本身清楚，GDD 齊全） | 中 |
| 程序化場景 | 地形高度場、建築、樹石、地基墊（56 處 SurfaceTool） | 高 |
| 物理正確性重建 | §三-3 那一整批已修好的邊界情況 | **高，且風險最大** |
| 驗收體系重建 | 20+ 探針 ＋ 474 處 await 的等價物 | **高** |
| 美術資產 | 大多可直接進，材質要重做 | 低～中 |

資料層與 GDD（15 個 JSON ＋ 17 份文件）是唯一幾乎零成本帶走的部分。

## 五、建議

**不建議現在做整體遷移。** 三個理由，按重要性排序：

1. 最在意的痛點（立繪本人模型像不像立繪）**換引擎不能解**，解法是 64GB 那台的 `gen3d`。
2. 8GB 主力機跑 UE5 會拖慢迭代，而迭代速度是目前進度的命脈。
3. 30/30 章 0 FAIL 的物理正確性會歸零重踩，這是最貴的隱性資產。

### 分級替代方案

**A. 留在 Godot，針對痛點強化（成本最低，建議先做）**
- 渲染：Godot 4 有 SDFGI／VoxelGI，目前尚未認真調過；「材質太暗」多半是
  tint × 頂點色 × 貼圖三重相乘的參數問題（`_scatter_rocks` 的註解史就是證據），
  不是引擎上限。
- 資產：先把 `tools/gen3d` 在 64GB 那台跑出 ultra 檔位的 17 件模型——
  這是目前投資報酬率最高的一步，且與引擎選擇無關。

**B. 混合：UE5 只當「資產產線」（中等成本，值得考慮）**
- 在 64GB 那台用 UE5／其工具鍊做模型清理、IK Rig 重定向、動畫烘焙、材質烘焙，
  成品匯出 glTF/FBX 進 Godot。
- 拿到 UE5 動畫與資產工具的好處，不付「重建遊戲邏輯與驗收體系」的代價。

**C. 全面遷移（最高成本，若要做請先 spike）**
- 先在 64GB 那台做一個垂直切片，**實測**：編譯循環多久、headless 自動化能不能
  跑得動「走查 30 章」這種規模、8GB 那台能不能開編輯器。
- 用實測數字再決定，不要憑「UE5 畫面比較好」就整體搬。

## 六、使用者已拍板：走方案 B（2026-08-02）

使用者的動機是**動畫與載具品質**，因此結論收斂為
**「UE5 只當資產產線，遊戲本體留在 Godot」**。不做整體遷移。

### 為什麼這條路對這個動機最划算

動畫與載具品質的瓶頸都在**資產**，不在執行引擎：
- 動畫：目前是自寫 `Retarget.gd`（459 行）在**執行期**即時重定向 UAL mocap，
  每個單位生成都要重定向一次（日誌 `[rig] xxx 重定向骨對數=20`）。
  UE5 的 IK Retargeter 是產品級工具，且可以**預先烘焙**成各角色專屬動畫。
- 載具：目前是程序化低多邊形車體，UE5 的 Fab／Quixel 有大量可直接用的成品。

留在 Godot 就完整保住了 §三 那些「換引擎會歸零」的資產：474 處 await 撐起來的
驗收體系、30/30 章 0 FAIL 的物理正確性、免建置與手機可玩。

### 執行步驟（都在 64GB 那台做，8GB 這台不裝 UE5 編輯器）

1. **載具**：在 UE5／Fab 取得八機種的成品模型（坦克、戰機、攻擊機、武裝直升機、
   驅逐艦、登陸艦、飛彈快艇、潛艇），清理後匯出 glTF 進 `assets/models/vehicles/`。
   Godot 端已有現成接口：`Unit._try_build_from_art` 走
   `<cls>_hull.glb` ＋ `<cls>_turret.glb`（分件）或 `<cls>.glb`（整件），
   尺寸與碰撞盒由 `data/vehicle_look.json` 的 `length_m` / `collide_hl` / `collide_hw` 控制。
   **記得補 `collide_*`**：沒有它時碰撞盒會退回用模型 AABB 推算（見 §七）。
2. **動畫**：用 IK Rig ／ IK Retargeter 把 UAL 動作庫重定向到九名角色各自的骨架，
   **烘焙**成每角色一組動畫，匯出 glTF/FBX。
3. **Godot 端接手**：改成直接播放烘焙好的動畫，`Retarget.gd` 的執行期重定向可退役。
   附帶好處：省掉每單位一次重定向的成本，且動畫姿勢變成**確定性**的——
   目前「跑步手垂直向下」這類問題正發生在執行期重定向／IK 這條鏈上。
4. 每一批資產進來後跑 `VehicleProbe` ＋ 一次全量重跑（載具改動會影響碰撞）。

### 不做的事

- 不遷移遊戲邏輯、不遷移驗收體系、不在 8GB 這台裝 UE5 編輯器。
- 不因為 UE5 有 Lumen 就把渲染搬過去；「材質太暗」留在 Godot 解
  （多半是 tint × 頂點色 × 貼圖三重相乘的參數問題，見 `_scatter_rocks` 的註解史）。

## 七、施工時要小心的既有陷阱

- **`collide_hl` / `collide_hw` 一定要在 `vehicle_look.json` 補齊**：
  缺這兩欄時碰撞盒改用模型 AABB 推算，而 AABB **含砲塔與砲管**——
  2026-08-02 就是這樣讓碰撞半長變成 4.39m（人在車頭 2.5m 外撞上一面看不見的牆），
  同一個錯還讓縮放基準用了含砲管的全長、整台車被縮小三成。
  已改成以 hull 為基準，但明確給資料仍然最穩。
- **船的碰撞盒不可沿用坦克數字**：驅逐艦 18m 長，用 6m 盒＝船身大半沒有實體。
- **匯入的模型若自帶動畫，會改走另一條路徑**：`Unit.spawn` 對「有 AnimationPlayer
  且動畫非空」的模型不做 UAL 重定向，姿勢改由 `skeleton_updated` 驅動。
  角色動畫烘焙完進來時，這條分支會第一次被真正走到——要一併驗。
